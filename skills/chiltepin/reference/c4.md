# C4 diagrams — the zoom story

Part of the **chiltepin** skill (the hub is `SKILL.md`, one folder up). Read
this file when a doc shows one system at more than one C4 level, or when a
`c4` diagram looks crowded. Run `chiltepin block c4` for the fields.

## One system, one question per level

| Level | The question it answers | Elements | Boundary |
|---|---|---|---|
| `context` | Who uses the system, and what does it depend on? | `person`, one `system`, `external` | none, or the enterprise |
| `container` | What runs, and who calls whom? | `person`, `container`, `store`, `external` | the system |
| `component` | Where does each rule live in one container? | the callers, `component`, `store`, `external` | the container |
| dynamic | In what order do the parts act in one scenario? | only the parts of that scenario | the level's boundary |

Write the levels top down, and open each section with its question. The
heading states the answer as a claim ("One API owns every write"), not the
level name. Stop at the level that answers the reader's question: most docs
need context and container only.

## Keep one name for one element at every level

- The system in the context view becomes the `boundary` label of the
  container view. The container you zoom into becomes the `boundary` label
  of the component view.
- Copy each name and description word for word from level to level.
- People and external systems keep their names and descriptions too.

## Write the elements

- `name` is the noun the team uses. `tech` names the technology; the
  renderer prints `[Container: tech]`. `desc` is one sentence of
  responsibility, in the present tense.
- `family` sets the shape and the hue: `web`, `browser` or `spa` draws a
  browser window; `mobile` a phone; `queue`, `topic` or `stream` a pipe;
  `db`, `cache` or `bucket` a cylinder. A `store` is always a cylinder.
- `external` means the team does not build or deploy it. A container the
  team runs is a `container`, even when a vendor wrote it. Set
  `family: external` on a person or a container outside the scope.
- In a component view, the callers are containers outside the boundary.
  A database the components use is a `store` outside the boundary.

## Write the relationships

- `label` states the intent in the caller's voice: "Reads from and writes
  to", "Sends e-mail using", "Makes API calls to". "Uses" alone says nothing.
- `tech` names the protocol (`JSON/HTTPS`, `SQL`, `AMQP`). Give it on every
  container and component relationship.
- Draw one arrow, from the caller. The reply is implied. Mark a message that
  does not wait for a reply as `kind: dashed`.

## The dynamic view

- Give `step: 1`, `step: 2`… to the relationships of one scenario, in order.
  The eyebrow then says "Dynamic diagram" and the key explains the numerals.
- Set `level` to the level the scenario plays at, and keep its `boundary`.
- Show only the elements the scenario touches. Four to nine steps read well;
  split a longer scenario at a hand-off.
- A relationship that two steps share needs two edges, one per step.

## Layout

- Omit `col` and `row` on every node. Auto-layout puts the people on top,
  the scope in the middle, and its dependencies below it or beside it.
  `dir: LR` turns the diagram on its side.
- Place nodes by hand only when the same shape must repeat across levels.
  Then keep every element of the boundary in one block of cells.
- Past about 12 elements or 15 relationships, split the view: one container
  view per subsystem, or one dynamic view per scenario.
